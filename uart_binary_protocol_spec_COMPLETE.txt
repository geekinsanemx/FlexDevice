UART BINARY PROTOCOL SPECIFICATION v1.0 FLEX-FSK-TX (ESP32 <-> HOST)

================================================== 1. OBJECTIVE
==================================================

Define a robust asynchronous binary protocol over UART for communication
between:

-   Host (Raspberry Pi / Python / C)
-   Device (ESP32 Heltec)

Requirements: - Full-duplex async - Non-blocking - Error tolerant (CRC +
retries) - Eliminate race conditions - Support concurrent operations -
Maintain legacy AT command interface (human interaction)

================================================== 2. ARCHITECTURE MODEL
==================================================

Message-Oriented Protocol (MOP)

Message Types: - CMD (Host → ESP32) - RSP (ESP32 → Host, immediate
acknowledgment) - EVT (ESP32 → Host, async events)

Flow Example:

HOST ESP32

CMD_SEND_FLEX ───────► ◄─────── RSP_ACK (accepted) ◄───────
EVT_TX_STARTED ◄─────── EVT_TX_DONE

================================================== 3. TRANSPORT LAYER
==================================================

UART: - Baudrate: 115200 - 8N1 - Full duplex

Framing: - COBS (Consistent Overhead Byte Stuffing) - Frame delimiter:
0x00

Frame: [COBS_ENCODED_PACKET] 0x00

CRC: - CRC16-CCITT - Polynomial: 0x1021 - Init: 0xFFFF

================================================== 4. PACKET STRUCTURE
==================================================

struct Packet { uint8_t len; // total length (excluding COBS delimiter)
uint8_t type; // CMD/RSP/EVT uint8_t opcode; // command uint8_t flags;
// control flags uint8_t seq; // transport sequence uint16_t msg_id; //
application ID uint8_t payload[N]; // variable uint16_t crc16; //
integrity }

------------------------------------------------------------------------

Field Definitions:

type: 0x01 = CMD 0x02 = RSP 0x03 = EVT

------------------------------------------------------------------------

opcode:

0x01 = SEND_FLEX 0x02 = GET_STATUS 0x03 = ABORT 0x04 = SET_CONFIG 0x05 =
GET_CONFIG 0x06 = PING

------------------------------------------------------------------------

flags:

bit0 = ACK_REQUIRED bit1 = RETRY bit2 = ERROR bit3 = PRIORITY

------------------------------------------------------------------------

seq:

-   0–255 rollover
-   transport-level ACK tracking

------------------------------------------------------------------------

msg_id:

-   GENERATED BY HOST
-   UNIQUE per operation
-   REQUIRED for async correlation

================================================== 5. COMMAND
DEFINITIONS (DETAILED)
==================================================

  ----------------------
  CMD_SEND_FLEX (0x01)
  ----------------------

Description: Send FLEX message (equivalent to AT+MSG)

payload: { uint64_t capcode; float frequency; int8_t power; uint8_t
maildrop; uint8_t msg_len; char message[msg_len]; }

Behavior: - Device enqueues message - Does NOT transmit immediately
(queue based) - Returns RSP_ACK

  -----------------------
  CMD_GET_STATUS (0x02)
  -----------------------

payload: none

Response: RSP_STATUS

  ------------------
  CMD_ABORT (0x03)
  ------------------

payload: none

Behavior: - Abort current transmission - Clear pending operation

  -----------------------
  CMD_SET_CONFIG (0x04)
  -----------------------

payload example: { float frequency; int8_t power; uint64_t
default_capcode; }

  -----------------------
  CMD_GET_CONFIG (0x05)
  -----------------------

payload: none

Response contains full config

  -----------------
  CMD_PING (0x06)
  -----------------

payload: none

Response: EVT_PONG

================================================== 6. RESPONSES
==================================================

  ---------
  RSP_ACK
  ---------

payload: { uint16_t msg_id; uint8_t status; }

status: 0x00 = ACCEPTED 0x01 = REJECTED 0x02 = QUEUE_FULL

IMPORTANT: ACK = received and queued NOT execution result

  ------------
  RSP_STATUS
  ------------

payload: { uint8_t device_state; }

device_state: 0 = IDLE 1 = WAITING_DATA 2 = WAITING_MSG 3 = TRANSMITTING
4 = ERROR

================================================== 7. EVENTS (ASYNC)
==================================================

  ----------------
  EVT_TX_STARTED
  ----------------

payload: { uint16_t msg_id; }

  -------------
  EVT_TX_DONE
  -------------

payload: { uint16_t msg_id; uint8_t result; }

  ---------------
  EVT_TX_FAILED
  ---------------

payload: { uint16_t msg_id; uint8_t error_code; }

  -------------
  EVT_ABORTED
  -------------

payload: { uint16_t msg_id; }

  ----------
  EVT_PONG
  ----------

payload: none

================================================== 8. ERROR CODES
==================================================

0x01 = INVALID_PARAM 0x02 = QUEUE_FULL 0x03 = RADIO_ERROR 0x04 = TIMEOUT
0x05 = BUSY

================================================== 9. RELIABILITY MODEL
==================================================

Transport Layer: - CRC validation - SEQ tracking - Retries (timeout
100ms) - Duplicate detection

Application Layer: - msg_id correlation - async event delivery

================================================== 10. TIMING
==================================================

ACK latency: < 10ms Retry timeout: 100ms Event timing: asynchronous

================================================== 11. ASYNC BEHAVIOR
EXAMPLE ==================================================

HOST: msg_id = 0x42 CMD_SEND_FLEX →

ESP32: ← RSP_ACK (0x42)

Later: ← EVT_TX_STARTED (0x42) ← EVT_TX_DONE (0x42)

================================================== 12. LEGACY AT SUPPORT
==================================================

-   AT commands remain available
-   Used for human/manual control
-   Binary protocol used for machine interface

Modes: - Binary (default) - AT text

Switch: AT+TXT AT+BIN

Both coexist logically.

================================================== 13. DESIGN PRINCIPLES
==================================================

1.  Every message has msg_id
2.  Never block
3.  ACK != execution
4.  Events = results
5.  Host manages state
6.  Device is event-driven

================================================== 14. PROTOCOL
COMPARISON ==================================================

Closest equivalents:

-   MAVLink (very similar)
-   HDLC (framing concept)
-   CAN bus (async message model)
